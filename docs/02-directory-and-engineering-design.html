RDWS_HOME 由配置固定为绝对路径，独立于代码仓库；开发默认用户目录下 .rdws，Linux 可配置到服务账号可管理的持久目录。运行数据不进 Git。模板在代码仓库 config / dsh/profiles，运行根 config 是非敏感部署配置；业务角色与需求状态以 PG 为准，不能靠 YAML 再维护一套。

一个项目对应一个 DSH 实例，每实例独占 DSH_HOME，内部文件布局由锁定上游管理；一个需求对应一个 workspace，会话 header cwd 精确为需求根。子任务、人员与会话共用同一组需求工作树，不创建二级并行树。.git 指向需求私有 .gitstore，不指向 sources；Plan 不是只读强制执行点。

新增 integrations 为平台受控的集成检出区；新增 state/deliveries 用于封存证据，PG 存不可变映射 / 校验值。artifacts 是可继续生成的工作产物，不充当不可变快照。runtime/instances 只保存进程元数据，不能成为第二套业务写权限真相；需求临时 .rdws 不存权威授权。

PG 数据放 Docker 命名卷，不置于 RDWS_HOME。使用独立 Compose project、PG18 固定镜像、仅本机端口、开发 / 测试数据库、非超级应用账号与迁移角色；镜像 18 挂载路径须依据锁定镜像核实。私有凭据权限 600，不输出连接串；不碰现有其他项目容器与卷。

已落地：原生服务只接入预置项目 poc。该项目实例目录为 runtime/dsh/project-poc/，会话工作目录为 projects/poc/demands/<requirement-id>/；进程锁与导出分别位于 runtime/instances/、state/exports/。测试运行目录独立。sources/、私有 Git worktree、写交接、集成检出和交付快照仍是目标结构。

11.6 Web 会话接入实施计划

用户授权将原生会话创建与流式响应接入工作台并验证两道闸。沿用已批准范围，最小补齐 Requirement / Participant / NativeSessionMapping 与 Web 需求创建入口；不扩展子任务、状态推进、代码写、部署或 GitLab。普通成员按需求参与读，项目管理员仅项目内管理读，只有本人会话可发送消息；全局保持只读及执行工具禁用。

浏览器 → Better Auth / PG 授权的 BFF → HMAC 短期非 owner Peer → 原生 RemoteAccessPolicy / Workspace / Session。cap 含 issuedAt、expiry（最多20秒）、nonce、项目 audience、登录会话与需求、真实workspace ID、可读 / 自有session集合；浏览器不持有原生票据。Host同步验签、读取不可变cap，过期或经私有签名端点撤销时先deny再dispose Peer并关升级socket。BFF定期复验、先停止转发再撤销 / 关流；撤销通知失败不得宣称立即一致，最迟以Host租约到期为界。

workspaceRegistry.create 返回的真实 ID 落PG。browser cap不允许session/create；BFF专用create cap仅在精确workspace资源上授权，参数只允许服务器workspaceId，不接受客户端cwd、preset或sessionId复用。native成功、PG映射失败时不给浏览器访问权、记录孤立ID，不无界重试；成功后撤旧Peer、重新鉴权重连，不热扩权。HTTP每个动作与WS每次logical open用同一显式允许表，未知拒绝；文件、附件存储、插件与供应商设置均不开放。

原生rdws Profile作为Web主入口，保留模型 / credentials；SDK探针改为独立原生probe Profile，直接引用同一模型patch，不复制配置。Web通过公开bootInjections / modules runtime、共享平台模块和ctx.sessions binding / eventSource消费原生transient settlement、恢复与重连，RDWS React自绘；不重新实现消息或Mux协议。

顺序：模型迁移与授权测试 → Native Web Host / non-owner Auth / Policy → BFF HTTP / WS与需求 / 会话入口 → 原生客户端和React → 真GLM浏览器及越权回归 → 台账证据。验证包括匿名 / 跨项目需求 / 他人会话写拒绝，list/control/history隔离，绕过BFF的native拒绝，已开流到期关断、退出撤权和通知失败、超过20秒真实响应跨generation无重复且刷新恢复。失败恢复保留数据和原生配置，关闭确认前不释放项目实例锁。

计划审阅：全新上下文A面（正确性 / 原生客户端可行性）与B面（安全 / 授权）均在修订后APPROVE；已吸纳创建专用cap、真实workspace映射、PG失败不扩权、不可变短Peer、主动关流和issuedAt撤销截止点。此为计划批准，不代表实现或验收已通过。执行证据后续追加。

安装包事实修订：发布的 rc.3 Connection 仍内置 BrowserAuth，不具备参考工作树中的 connection.authentication / webserver/authorize 接口。两面撤回基于新工作树的批准后，重新审核已安装源码并批准公开载体组合：独立 /_rdws 路由验签、显式non-owner Peer，复用 createSharedFetchHandler.fetch(request,peer) 与公开导出的 RemoteStreamMuxServer / wireStream。HTTP精确映射到/api原生路径，同generation HTTP/WS复用同cap与Peer。内置owner管理入口实际仍存在，仅loopback且不由BFF代理，不声称已关闭；普通用户无其Token/Cookie。公开源码导出用tsx加载，不修改上游或私有认证映射。此修订保持用户两道闸目标，真实拒绝和旧入口隔离仍须实测。

11.7 Web 会话接入实际落地与验证

结果与边界见 台账 §8.7。工程沿用 §11.1 目录：dsh/client 收口浏览器原生模块适配，dsh/host/web.ts 启动项目级子进程，dsh/bridge/access.ts / wire.ts 管授权与帧准入，dsh/plugins/rdws-access 承载原生策略和私有载体。业务 BFF 位于 apps/server/src/modules/workbench.ts，自绘会话位于 apps/console/features；三张业务映射表及迁移归 packages/db。未预建 orchestrator / syncer 或复制上游源码。

原生客户端：从安装产物的公开入口加载 bootInjections、modules runtime、Session binding 与 eventSource，保留原生 history / transient / settlement 语义。按发布包实际 ABI 处理静态模块 namespace、reconnect()、refresh() 与模块 import 参数，不照搬不同提交的参考树。每次物理重连产生新 generation，PG 重新鉴权；保留同一 Cordis 根，原生会话恢复后继续消费流，避免旧 Binding 与重复历史。Native Store 所需 Zustand / Immer 是上游运行依赖，不改变 RDWS 的 Query / 局部业务状态选型。浏览器 Node 模块边界明确失败，不提供文件系统能力。

两道闸：浏览器只访问 BFF。HTTP / WS 使用同一允许表和同 generation 不可变签名能力；默认拒绝未知方法、文件 / 插件 / 供应商设置与 uplink item。Host 在独立 /_rdws 路由验签，以 non-owner Peer 调公开 createSharedFetchHandler.fetch(request, peer) 与包 exports 公开的 RemoteStreamMuxServer，后者由 tsx 加载。内置 owner 入口仅 loopback，既未关闭也未代理。真实 workspace ID 由原生注册表返回后落 PG；原生创建成功而 PG 映射失败时保留孤立 ID 证据并拒绝浏览器准入，不热扩权。

租约和关闭：能力有效期最多 20 秒；Host 先 deny 后 dispose Peer 并关 socket。退出先同步标记登录会话 closing，禁止等待期间新准入，再终止 BFF 在途 HTTP / WS、通知原生撤销；通知不可达时以租约为原生关断上界。scope epoch 防止异步旧准备结果发票，HTTP 返回前再鉴权，拒绝撤权前已取得的旧响应。正常关闭在 Fastify preClose 中先关桥与子进程，再释放锁；锁恢复仅在父子 PID 都确认停止后允许，未知状态拒绝，原生日志不删除。

只读修正：只在根禁用 tool-* 并不足够，原生 standard 等 preset 会在会话作用域重新注册执行工具。已先以原生 request/header 断言复现，再加入 dsh/profiles/web-readonly.cordis.yml 清空 standard / minimal / ptc / cordis 的 plugins，配合 serial agent/created 限制继承工具与根 tools.guard 拒绝执行。overlay 顺序为原生模型配置、只读基础策略、preset 限制、Web 载体。新建真实会话验证请求 header 有记录且工具集合为 0；旧会话快照可能保留工具声明，由执行 guard 拒绝，不重写历史。

运行空间：日常 Web 沿用 ~/.rdws/runtime/dsh/project-poc 的 rdws Profile 和原生凭据；SDK 探针 rdws-probe 引用同一模型 patch，并共用项目进程锁。真实浏览器测试的数据 / 实例分别在 ~/.rdws/testing-web、testing-fault，通过原生路径引用模型 / 凭据，不复制密钥，不覆盖日常 Web / API 端口。最终测试进程组退出后曾遗留锁文件；父子 PID 均确认已停止后，已通过既有受控锁恢复分支清理。PG 仍为本机 Docker 的独立开发 / 测试库；测试需求和原生轨迹保留以便复查，不自动清空。

  7. 历史回放：首次公开 session/events 读取捕获逻辑边界 C，后续固定 throughSeq=C、以已读最小 seq 作为 beforeSeq 向前分页；从 dsh/client 适配使用被动读取，不借 retain / follow(activate:true) 激活恢复。按 Native seq 展示逻辑历史、边界、加载进度、空态和重试；超出已加载范围不得称为完整历史。冷读的内存恢复补齐可能属于该逻辑视图，不能逐条冒称磁盘记录。时间线仅渲染白名单类型的安全摘要与对话文本，不直接展示 principal、票据、上下文内部载荷或原始 JSON；文本保持 React 转义。实时 transient 帧不混入固定回放。回放与翻页不创建运行绑定、不调用 prompt、不追加会话事件；离开后释放请求，源会话仍可独立运行。正常重新打开会话的激活恢复可能持久补齐日志，不能把它当作被动回放证据。

0评审结论

总体判定

方向对、分层对，尤其「项目即租户」「需求才是工作目录」这两个判断与 DSH 的原生模型高度契合。但当前目录设计有 4 个结构性问题会持续制造返工：① 与 DSH workspace 概念撞名；② 缺运行时目录（DSH_HOME 必须有独立落点）；③ 缺控制面数据的归属说明（目录不等于 RBAC）；④ sources「不允许直接改动」与 git worktree 的元数据写入天然矛盾。

另外要修正我上一轮的一处粗略结论：不必「每需求一个 DSH 实例」。核查发现 workspaceRegistry.create(path, title) 幂等且一个实例可注册多个 workspace，因此默认按项目（租户）分片一个实例，按需升级为需求级实例更合理。详见 §5。

最漂亮的一点

把 demand-A 整个目录作为 DSH workspace，sources 置于 workspace 之外 —— DSH 的 workspace-write 沙箱以会话 cwd 为写入边界，物理上就实现了「唯一事实源不可由 AI 直接改动」，不靠约定、不靠自觉。

最需要替换的一点

「worktree 建在 demand 下、直接挂在 sources 主仓」做不到零写入：git 的 worktree 元数据必然写进主仓 .git/worktrees/，且 DSH 内置 worktree 插件的检出池是源仓库内部相对路径。推荐改为需求级私有 bare 仓库 + worktree（§3，已实测）。

必须补的一层

runtime/：每个实例的 DSH_HOME（profile、凭据、会话日志、插件、SQLite）、进程状态、锁、缓存。它与业务数据的写频率、备份策略、保密级别完全不同，混进 config 或 demands 会出事故。

最容易被忽略的并发问题

一个需求下「很多 AI 会话」若共用同一个 worktree，并发写会互相覆盖。DSH 允许同一 workspace 下多会话并行，所以必须由平台加需求级写锁：同一时刻仅一个写会话，其余会话跑 read-only / 评审模式。

3分支与 worktree 管理（你问的重点）

3.1 先说清矛盾在哪

git worktree add 会在主仓库的 .git/worktrees/<name>/ 下登记 HEAD、index、gitdir 等元数据；worktree 里的 .git 是一个含绝对路径的文件，指回主仓库。所以「worktree 放在 demand 目录、主仓 sources 完全只读」这两个要求，在原生 worktree 下不能同时成立。此外 DSH 自带 @deepseek-ai/dsh-experimental-worktree 的配置项 directory 明确是「Relative checkout pool inside the source repository」，默认检出到 <current checkout root>/.agents/worktrees/<name>，且文档写明「创建操作不会扩大目标目录或共享 Git 管理目录的写权限」—— 在 workspace-write 沙箱下让 AI 自己跑这个工具会被拒，不适合作为 RDWS 的需求主工作树方案。

3.2 三个方案对比

方案做法利弊结论
A主仓 sources 直接 worktree add 到 demand最简单、对象零复制主仓 .git/worktrees/ 被写 → 违反「唯一事实源不可改动」；并发 add 有锁竞争；AI 容器必须挂载可写 sources否
B每需求独立 git clone完全隔离、.git 在 demand 内、AI 容器无需挂载 sources每需求一份完整对象库，大仓磁盘/时间成本高；基线冻结需额外处理备选
C需求私有 bare + worktree：git clone --bare --local 从 sources 到 demand/.gitstore/repo.git，再从私有 bare worktree add 到 demand/worktrees/repo--local 硬链接共享对象，几乎零额外磁盘；gitdir 全在 demand 内；sources 只被读一次；需求级 refs 与分支天然隔离；归档删目录即彻底清理平台侧多一层编排；跨文件系统时 --local 退化为复制推荐

3.3 方案 C 实测结果（本机 git 验证）

# 1. 唯一事实源（只读 bare mirror）
sources/repo-a.git/

# 2. 需求创建时，平台编排层执行（AI 会话不参与）
git clone --bare --local \
  /abs/.rdws/projects/project-A/sources/repo-a.git \
  /abs/.rdws/projects/project-A/demands/demand-A/.gitstore/repo-a.git

git --git-dir=/abs/.../demand-A/.gitstore/repo-a.git \
    worktree add -b rdws/demand-A/repo-a \
    /abs/.../demand-A/worktrees/repo-a <baseCommit>

# 3. 需求完成后：发起 MR → CI → 合入 baseline；归档时
git --git-dir=/abs/.../.gitstore/repo-a.git worktree remove .../worktrees/repo-a
验证项实测结果
对象是否共享--local 后 origin 与 demand 私有 bare 的对象文件 inode 相同（硬链接），无额外对象复制
worktree 的 .git 指向gitdir: /.../demand-A/.gitstore/repo-a.git/worktrees/repo-a —— 完全在需求目录内
AI 在 worktree 内能否提交可以，git commit 成功，新提交落在需求分支 rdws/demand-A/repo-a
唯一事实源是否被改动origin HEAD 与基线一致、refs 仍只有 main、主仓 worktrees 登记数 = 0；需求私有 bare 登记数 = 1
结论：方案 C 让「sources 是唯一事实源、不允许直接改动」从约定变成物理事实 —— AI 容器只需挂载 demand-A 一个目录，连 sources 都不必挂载。

3.4 分支规范与生命周期

环节规则
基线项目级 config/projects/project-A.yaml 声明 baselineBranch（如 develop）；创建需求时解析为 不可变 baseCommit 写入 demand.yaml。
分支命名rdws/<demand-id>/<repo>；多仓库需求下每个 repo 一条同名分支。禁止 AI 自行 checkout -b 到基线分支。
创建主体只能由平台 orchestrator 执行（唯一有 sources 读权限与 git 操作权限的组件）；AI 会话创建前工作树已就绪。
并发写同一 demand 下多会话共用同一批 worktree，必须加需求级写锁：同一时刻一个写会话（workspace-write），其余会话以 read-only（设计/评审/测试分析）运行。需要真正并行写代码时，由平台按会话派生二级 worktree（rdws/<demand>/<session>/<repo>）并在合并点做显式归并，作为可选高级模式。
回主干平台发起 MR/PR → CI → 合入 baseline；AI 不直接 push。合并后 syncer 更新 sources mirror，其他活跃需求通过 git fetch 自行决定是否 rebase 基线。
归档状态机置为 archived → 停止会话 → 导出轨迹摘要到 artifacts/sessions/ → worktree remove（保留分支与提交，可配置）→ 按需整体冷备 demand 目录后清理 .gitstore。
运维坑：worktree 的 .git 文件写的是绝对路径。整体迁移 .rdws 或跨主机恢复备份后，必须执行 git worktree repair 或由平台重建 worktree；否则所有需求工作树同时失效。建议把「路径可重建」写进编排层，不把 worktree 当作可搬运资产。

5实例分片粒度（修正上轮结论）

上一轮我建议「每需求一个 DSH 实例」，是基于隔离最强化给出的粗略判断。核查 workspaceRegistry 后可细化如下：

粒度可行性取舍建议
全平台一实例否单 owner、单 DSH_HOME、跨租户无隔离，且所有会话单写者挤在一个进程排除
每项目（租户）一实例可行一个实例注册该项目下所有 demand workspace；挂载整个 project-A（sources 只读 / demands 可写）；共享项目级模型与凭据策略；资源开销 O(项目数)。代价：项目内所有成员在 DSH 侧仍是同一 owner，权限必须完全由平台 BFF 兜住默认

8关键数据流

  1. 项目初始化平台建 projects/project-A/{sources,demands} → syncer 把各仓库 git clone --bare --mirror 到 sources/<repo>.git → 写 config/projects/project-A.yaml（仓库清单、baseline、角色、隔离档位）。
  2. 需求创建 / 批量导入平台在 DB 建需求与指派 → 解析 baseCommit → orchestrator 建 demands/demand-A 目录树 → 按仓库执行 clone --bare --local + worktree add -b rdws/demand-A/<repo> → 生成 demand.yaml 与 AGENTS.md。
  3. 实例就绪launcher 按 InstanceSpec 渲染 runtime/dsh/<instance>（profile + patch + 凭据 + 插件）→ 拉起 dsh --profile rdws → rdws-workspace 对本项目所有 demand 调 workspaceRegistry.create() → 健康检查通过，登记路由表。
  4. 开发会话开发登录 → BFF 校验角色与需求权限 → 取需求写锁 → bridge createSession(cwd = demand-A 绝对路径) → attachSession() → rdws-demand-context 注入上下文 → AI 在 worktrees/repo-a 内编码（workspace-write 边界仍为 demand-A）→ 事件流写审计。
  5. 阶段流转与归档需求/开发/测试/部署角色在同一 workspace 开不同会话（读会话不占写锁）→ 平台发起 MR → CI → 合入 baseline → 归档时导出轨迹摘要、worktree remove、释放写锁、按策略冷备或清理 .gitstore。

P0会话 cwd 精确等于 demand 路径在 bridge/session.ts 断言并写契约测试；否则 attachSession 直接拒绝，会话会变成 Ungrouped。
P0需求级写锁 + 会话只读档位验收：两个并发会话中仅一个可写，第二个自动以 read-only 运行且不产生文件变更。
P1需求上下文不依赖 AGENTS.md 目录发现demand 目录无 .git 根标记，指令链上溯不稳定；用 agent.inject() 显式注入，$DSH_HOME/AGENTS.md 只放平台红线。
P1worktree 绝对路径与迁移备份/迁移后必须 git worktree repair 或由编排层重建；不要把 worktree 当可搬运资产。
P1并发 git 操作串行化同一 .gitstore 上的 worktree add/remove、以及 syncer 的 fetch，需平台侧加锁，避免 index/refs 竞争。
P1.gitstore 保护允许 git 命令写元数据，但用 rdws-policy 拦截文件工具对 .gitstore/ 的直接编辑/删除，防止 AI 破坏需求对象库。
P2上游版本与回归锁 0.2.2-rc.3 快照；dsh/tests 固定 profile 快照、会话归属、cwd 与沙箱策略用例，作为每次升级的门禁。
