0结论摘要

总体判定

有条件可行（Conditional Go）。DSH 适合作为「每个需求一个隔离的 AI 执行内核」，不适合被直接改造成多租户的平台后端。建议的路线是：外围自建业务平台（账号 / 项目 / 需求 / RBAC / 编排 / 审计），DSH 以「一需求一实例」的方式被调度，通过插件与配置扩展，不改内核。

开源许可本身不是障碍（MIT），真正的红线是数据外发、商标、第三方非宽松依赖、以及官方明确声明的「未做安全审计 / 不可用于生产」。二次开发难度呈两极：插件级改造较容易，账号体系与多租户隔离必须自建，且工作量主要在你的平台侧而非 DSH 侧。

问题一：开源使用风险

主体 MIT，内部使用与私有化改造无 copyleft 义务。但有 4 个必须处理的点：①「DeepSeek Harness」是注册商标，禁用于项目名；② 默认会把完整会话日志随官方模型 API 请求上传；③ 内含 Anthropic Claude Code CLI 二进制，授权是「项目所有者身份范围」而非宽松许可；④ MPL-2.0 / Apache-2.0 依赖的署名与源码提供义务。

问题二：二次开发难度

架构上「一切皆插件」，认证、授权、存储、沙箱、会话持久化、UI 全是可替换 seam，扩展路径清晰；但仓库 382 个包 / 约 3563 个 TS/Python 源文件、强制 Node ≥24.9 + pnpm 11、仍处于 rc 快速迭代（会话格式已到 v4）。不要 fork 内核，应锁定版本 + 插件扩展 + 外围平台。

最大架构约束

DSH 是「单进程 · 单 owner · 单 DSH_HOME · 会话单写者」模型。默认 Web UI 只监听 loopback、不支持 0.0.0.0，认证是「启动 URL 里的进程 Token → Cookie」，没有账号/租户概念。一个共享大进程承载全公司项目，既不安全也不可扩展。

最契合的一点

你的第 5 条需求几乎与原生模型一一对应：workspace = 规范目录 + 稳定 ID + 有序会话账本；session = append-only 事件日志，原生支持 resume / fork / replay / 搜索。需求 : 工作区 = 1 : 1，会话 : 需求 = N : 1，无需自研会话引擎。

1核查基线与对象定性

先把对象定义清楚，否则可行性判断会失焦：DSH 是 Agent Harness（智能体运行时），不是模型、不是推理服务、更不是研发管理平台。

2.2 关于「二次分发」的边界

如果平台仅在本企业内网自用的服务器上运行，不向外部主体交付二进制，MIT 的复制 / 署名义务基本只体现在保留源码声明，风险最小。若后续要把改造后的客户端或一体机交付给集团内其他法人、子公司或客户，性质可能转为「分发」，此时需逐项复核：MIT 与 Apache 的声明、MPL-2.0 对应源码可得性、以及 Claude Code payload 的授权是否覆盖你的主体 —— 官方已用「identity-scoped」措辞把该授权限定在项目所有者身份上，不能默认继承。稳妥做法是发布包中不含这些组件。

3二次开发难度

3.1 有利因素：扩展点是一等设计目标

docs/architecture.zh.md 明确「新行为附加到已有文档记录的扩展点」，并给出归属映射表。与你的需求直接相关的可替换 seam：

扩展点可做的事改造层级
ctx.connection.authentication.register(provider)替换默认 Token/Cookie 认证，注入企业身份（SSO / LDAP / OAuth2 校验后签发 Peer）插件，不改内核
PrincipalMap 声明合并身份类型默认只有 { kind: 'owner' }，但类型设计为 merge-extensible，各驱动可声明自己的 kind；可扩展出 enterprise-user 并落盘到会话日志类型扩展 + 插件
ctx.remoteAccess.registerPolicy(kind, policy)基于 role / binding / resource 的方法级 RBAC：Gateway 在解析参数前询问 decide()，列表结果逐项过滤，前端访问快照自动隐藏入口插件 + 策略注册
ctx.sessionPersistence seam替换会话持久化后端（随附为每会话一个 .jsonl.zstd 文件），可实现中心化后端后端实现，难度高
ctx.storage / storage-sqlite / storage-json非会话应用数据（含 workspace 记录）的存储可换后端后端实现，中等
ctx.sandbox / ctx.fs / ctx.shell把文件系统与子进程指向远程沙箱；官方说明「指向远程沙箱，Bash / PTY / LSP 一并搬过去」provider 替换，中等
ctx.llm 适配器、cordis.patch.yml profile接企业内网模型网关；启停插件、覆盖配置、定制 UI 组合配置级，低
SDK / headless / ACP / @RemoteTS 与 Python SDK 与同一 agent loop；Typert API Gateway 可声明业务方自己的一元 / 流式 Remote 方法；headless 支持一次性任务、Webhook 可外部触发 Session平台对接，中等
判断：你不需要 fork 内核。官方的扩展哲学是「把插件挂在旁边，而不是给内核打补丁」，这与企业定制的方向一致，是这套方案成立的最大理由。

3.2 不利因素：三个绕不开的硬约束

  1. 单进程单 owner 模型。packages/typert/protocol/src/types.ts 的 PrincipalMap 默认只有 owner；README 与 RemoteAccess 文档明确 owner 恒放行、从不受检查，非 owner policy 是为 liveshare 只读观众设计的。默认 host-authentication-token 是「启动 URL 带进程 Token → 换 Cookie → 共享一个 Peer」，浏览器与 API 共用凭据，30 天有效期。文档原话：「打印的 URL 携带进程凭据，只应与预期用户分享」「无论是公告 URL 还是栅栏都不保护监听端口本身」。这不是账号系统，把它改造成企业 RBAC 需要替换认证 provider、为每个 Remote 方法声明资源、写 policy，并规避 owner 旁路 —— 工作量中等偏高且容易留越权口子。
  2. 会话单写者 + 全局 DSH_HOME。session-persistence 约定「每个后端实例内每个会话只允许一个写入方」，同一 session 二次写打开抛 SessionAlreadyOwnedError；workspace 路径唯一性依赖宿主文件系统 realpath；RemoteAccess 文档甚至建议「需要不同读者使用不同图片存储时，须使用独立 Host 实例及各自的 DSH_HOME 目录」。结论：无法靠一个巨型共享进程做水平扩展，必须按需求 / 用户分片成多个实例，并做会话粘性路由。
  3. 沙箱不是多租户边界。packages/sandbox/README.zh.md 原文：「隔离仅适用于与宿主共享文件系统和内核的子进程；容器、microVM 与远程执行器会替换整个能力」。Landlock / bwrap / Seatbelt / Windows 受限令牌都是「同一台机器上的进程约束」，跨用户隔离必须靠容器 / VM 硬边界。

4五项需求逐条核验

#你的需求判定落地方式与注意点
1B/S 架构：后端跑主机，浏览器 / 客户端访问（Tauri 外壳？） 可行 官方 web profile 就是 Node HTTP Server + Web UI，支持 --public-url / --trusted-host / 原生 TLS / 反向代理，B/S 路径已被官方支持。但默认只监听 loopback，且明确「不支持 dsh web --host 0.0.0.0」，须由反向代理承载外部链路并保留 Host、剥离前缀、转发 WebSocket 升级、改写 Cookie 作用域。
关于 Tauri：官方桌面端是 Electron（apps/desktop/package.json 写明 "Electron desktop shell for a bundled dsh runtime"），且壳内打包完整本地 runtime，与「后端集中在主机」目标相悖。建议纯 B/S；若确需客户端，只做薄壳（Tauri / Electron 均可）承载 SSO、本地文件与终端，不要再跑一份 DSH。用 Tauri 替换 Electron 本身不难，但收益有限、不在关键路径。
2三类平台角色 + 四类阶段角色，一人多身份 需自建 DSH 没有账号、组织、租户、用户目录（packages/identity/ 下只有 anonymous-user-id）。角色模型（平台管理员 / 项目管理员 / 需求 / 开发 / 测试 / 部署，且一人多身份）应作为平台侧 RBAC 数据模型实现，与 DSH 无关。DSH 侧只保留两层：① 平台服务账号作为受控 Peer；② 用 RemoteAccessPolicy 做方法级兜底校验。不要把角色语义塞进 DSH 内核。
3一个账号具备多个项目权限 平台侧 典型 user × project × role 多对多授权表，平台侧解决。DSH 侧配合：按「需求实例」授权而非按进程授权，实例与项目绑定，天然避免跨项目越权。RemoteAccess 的资源种类（global / session / workspace 等）可作为方法级二次校验的挂载点。
4项目管理员批量导入 / 新增需求，并分配开发、测试 需自建 DSH 不提供业务需求管理。平台侧实现 Excel/CSV 批量导入、需求表、字段校验、指派与状态机；创建需求时由编排层异步触发：建代码分支 / worktree → 分配 workspace → 拉起 DSH 实例 → 预置 AGENTS.md 与需求上下文。可用 webhookRuntime / headless / SDK 作为触发与回写通道。注意 workspace 路径唯一性基于 fs.realpath，同一目录不能挂两个工作区，规划目录规范时要定死。
5每需求一个工作区，其下可创建大量会话持续与 AI 协作研发 高度契合 原生能力，几乎零改造。docs/subsystems/workspace.zh.md：workspace = 规范目录路径 + 稳定 UUID + 显示名 + 有序会话账本；docs/architecture.zh.md：session 为 append-only 事件日志，模型所见即所记录，支持 resume / fork / search / replay / 轨迹检视。映射为 需求 → 1 个 workspace → N 个 session 即可。但注意：会话单写者 + 单 DSH_HOME 意味着这些会话应由同一个专属实例承载，不能跨进程并发写同一会话；大需求可派生子会话（fork）而非并行写。

5.1 三条关键取舍

  • 为何不是「一个大 DSH 进程 + 多账号」：认证是进程 Token 共享 Peer、owner 恒放行、会话单写者、沙箱只限同宿主子进程 —— 四个假设都指向单用户本地工具。硬改成多租户，等于在别人的核心假设上反复打补丁，且每次上游 breaking change 都要重做。
  • 为何用 BFF 而不是替换 DSH 认证：可以替换 ConnectionAuthentication 并注册 RemoteAccessPolicy，但官方已知限制不少（精确 Fetch 路由对非 owner 一律 403、事件转发泄露 host 绝对路径、条件依赖 args 时快照与判定不一致等）。对内网生产系统，把鉴权放在平台层、DSH 只信任平台服务账号更可控，也更容易过安全评审。
  • 为何不用 Tauri 重写桌面端：客户端不是瓶颈；且官方 Electron 壳的价值在于「本地 runtime」，这恰恰与集中式后端冲突。薄壳仅在你确实需要本地文件拖拽、本地终端、离线提示时才有必要。

6分阶段落地与优先级行动清单

  1. P0 · 合规与安全基线（阻塞项，未过不得上线）① 锁定 0.2.2-rc.3 内部镜像 / vendor 快照；② profile patch 关闭 dsh-session-log-deepseek、遥测设 DISABLED；③ 模型统一指向内网网关，网络出口白名单，抓包验证无外发；④ 剔除 Claude Code SDK / mods 相关实验插件；⑤ 按《品牌资产使用规范》确定独立品牌名；⑥ 出具 MIT / Apache-2.0 / MPL-2.0 依赖合规清单；⑦ 全实例跑在一次性容器 / VM 中，遵循 SAFETY.md 的最小权限与备份要求。
  2. P1 · 最小闭环验证（PoC，验证「需求 → 工作区 → 多会话」）单项目、单需求、单实例：用容器起 dsh web，通过 BFF 代理访问；手工创建一个 workspace，验证在其下创建 / 恢复 / fork 多个 session、轨迹检视、审批与沙箱策略；接内网模型网关完成一次真实需求研发。此阶段不写 RBAC，先把 DSH 能力边界跑实。
  3. P2 · 平台侧主体建设用户 / 项目 / 角色 / 需求 / 分配 / 批量导入 / 审计的数据模型与接口；企业 SSO；需求状态机；与 需求 ↔ 实例 编排打通；UI 品牌化与入口裁剪。此阶段与 DSH 基本解耦，可独立排期。
  4. P3 · 多实例编排与隔离容器模板（独立 DSH_HOME / 代码挂载 / 资源配额）、实例池与空闲回收、会话粘性路由、持久卷与备份、监控告警、配额与成本统计。先单实例后分片，不要一开始就做分布式会话存储。
  5. P4 · 可选增强若确实需要 DSH 直连浏览器：实现 AuthenticationProvider + enterprise-user principal + RemoteAccessPolicy，并为所有 @Remote 方法补齐 resources 声明。若需要跨会话检索 / 统一报表，再评估自研 SessionPersistence 后端（难度高，建议先把 JSONL 落盘 + 旁路同步到数仓，而非替换 seam）。
